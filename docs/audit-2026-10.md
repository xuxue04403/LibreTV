# 代码审计报告（2026-10）

审计范围：`packages/core`、`apps/desktop`、`apps/androidtv` 的全部源码约 1.1 万行。
方法：静态检查（TypeScript strict、ESLint、Android Lint）+ 人工逐文件复核 + 对真实采集源与本地 mock 的实测复现。

结论：**发现 12 处真实缺陷（含 5 处高危）**，全部已修复并补上回归测试。桌面端打包体积从 35.1 MB 降到 2.0 MB。

---

## 一、安全

### S1 媒体代理可用重定向绕过 SSRF（高危，已修）

`apps/desktop/src/main/proxy.ts` 原本用 `redirect: 'follow'`，而地址校验只发生在入口：

```ts
// 修复前
const init = { method: 'GET', headers, redirect: 'follow' };
const upstream = await fetch(targetUrl.href, init);   // 302 之后不再校验
```

已本地复现：入口是合法公网地址，302 跳到 `http://127.0.0.1:<port>/admin`，代理会原样取回内网内容。任何采集站或恶意 m3u8 都能把它当内网探测跳板。

**修复**：改为 `fetchChecked()`，`redirect: 'manual'` 逐跳跟随，**每一跳都重新执行 `assertAllowedTarget`**，并把跳转次数限制为 3 跳。

### S2 `http:fetch` IPC 是完全无校验的后门（高危，已修）

`apps/desktop/src/main/index.ts` 里 `http:fetch` 直接 `fetch(url)`：没有协议检查、没有内网检查、`method` 可为任意值、响应体无上限。代理精心做的 SSRF 防护在这条通道面前等于不存在。

**修复**：复用 `assertAllowedTarget`（同样尊重 `LTV_ALLOW_PRIVATE_MEDIA` 联调开关）、method 限定 GET/POST、响应体上限 16 MB（超限返回 413）。

### S3 DLNA 控制地址未做同源限制（中危，已修）

`discoverDevices` 接受 SSDP 回包里任意 `controlURL`，`castToDevice` 直接对它 POST SOAP。局域网内任意主机都能把自己伪装成渲染器，把 SOAP 引到别的主机。

**修复**：① 只接受与 socket 本地地址同网段的 SSDP 回包；② `controlURL` 必须与 `location` 同源；③ `dlna:cast` IPC 侧再复核一次同源，不信任渲染层传入的 device 对象。

### S4 图片代理会把 `text/html` 当图片返回（中危，已修）

`/i` 路由原样透传上游 `Content-Type`，且缓存 24 小时。上游返回 `text/html` 时，等于允许在 `http://127.0.0.1:<port>` 这个源里执行脚本——而 token 就在该源的路径上。

**修复**：`/i` 只放行 `image/*`，其余统一 `application/octet-stream`；所有响应加 `X-Content-Type-Options: nosniff`；缓存降到 1 小时。

### S5 渲染进程沙箱与 CSP 均可收紧（中危，已修）

- `webPreferences.sandbox: false` → 改 `true`（preload 只用 `electron` 模块，无需 Node 环境）。
- CSP 缺 `object-src`/`base-uri`/`frame-src`/`form-action` → 补齐 `object-src 'none'; base-uri 'self'; frame-src 'none'; form-action 'none'`。

## 二、内存与资源

### M1 `MAX_BODY_BYTES` 形同虚设（高危，已修）

```ts
// 修复前
const len = Number(res.headers.get('content-length') || 0);
if (len > MAX_BODY_BYTES) throw new Error('响应体过大');
const buf = Buffer.from(await res.arrayBuffer());   // ← 已全量进堆，判长只是事后检查
```

三个问题：① 判长发生在全量读取之后，挡不住 OOM；② `content-length` 缺失（chunked）时 `len = 0` 直接放行；③ `/p` 对非播放列表同样整段缓冲，一个 1 GB 直链 mp4 会同时驻留 3 份副本（`readLimited` → `toString` → `Buffer.from`）。

**修复**：`readLimited` 改为 `for await (const chunk of res.body)` 流式累加，超限立即 `body.cancel()`。

### M2 DLNA 接收端可被单个请求打崩（高危，已修）

```kotlin
// 修复前
val length = headers["content-length"]!!.toInt()
val buffer = CharArray(length)      // ← 客户端说多大就分配多大
```

一个 `Content-Length: 1000000000` 就能让电视 OOM。同时 `thread { handleClient(client) }` 每连接一线程、无 `soTimeout`、无上限。

**修复**：请求体上限 64 KB、`soTimeout = 5s`、头部数量上限 64、固定 4 线程的 `ExecutorService`，并在 `stop()` 时 `shutdownNow()`。

### M3 打包进 20 MB 无用 source map（已修）

`electron-builder.yml` 的 `files` 只列了 `out/**` + `package.json`，但 electron-builder 仍会按生产依赖打包 `node_modules`。实测 app.asar 35.1 MB，其中 `hls.js.map` 3.33 MB、`hls.mjs.map` 3.3 MB 等约 20 MB 全是 source map——而 hls.js 早已被 vite 打进 renderer bundle。

**修复**：`files` 增加 `!node_modules/**`、`!**/*.map`、`!**/*.ts`、`!**/*.md`。**app.asar：35.1 MB → 2.0 MB**。

> 体积骤降是否合理，用实测而非推理确认：renderer bundle 1.97 MB 内含 `Hls` 与 `mpegts` 特征串；打包产物实跑播放得到 `video: t=3.22 dur=158.80 paused=false ready=4 src=blob:` —— `blob:` 说明 hls.js 已用 MSE 接管播放。

## 三、功能正确性

### F1 DLNA 接收端完全不可用（高危，已修）

这是最严重的一处：手机能发现设备，但点投屏毫无反应。

```kotlin
// 修复前 —— SOAP body 里根本没有 Action 这个元素
val action = extractTag(body, "u:Action") ?: extractTag(body, "Action") ?: ""
```

UPnP 的动作名在 HTTP 头 `SOAPACTION: "urn:...:AVTransport:1#Play"` 里，或作为 `<s:Body>` 下的第一个元素名。取不到 → `action` 恒为 `""` → 全部落到 `else` 分支 → `SetAVTransportURI` 永不执行。

同时 `soapResponse` 把响应的 `xmlns:u` 硬编码为 AVTransport，RenderingControl / ConnectionManager 的响应不符合协议，部分控制点会判为非法响应。

**修复**：`resolveAction(headers, body)` 优先读 `SOAPACTION` 头，回退到解析 `<s:Body>` 的第一个元素名；`soapResponse(service, action, payload)` 按服务传入正确的 URN。

### F2 分类浏览没有成人过滤（高危，已修）

`searchSources` 有 `filterAdult`，`browseCategory` 完全没有。而「伦理片」名字带「片」，会被归入「电影」桶——首页分类直接露出成人内容。

**修复**：`browseCategory` 增加 `filterAdult`（默认 true），对合并后的结果调用 `filterAdultResults`；桌面端与 TV 端都接上 `settings.adultFilter`。

> 这个 bug 是 ESLint 发现的：`Category.tsx:32` 的 `adultFilter` 变量「已赋值但未使用」——说明当初设计了却没接上。

### F3 播放器实例复用导致投屏错播（中危，已修）

```kotlin
// 修复前：key 是 Unit，URL 变了也不重建
val exo = remember { ExoPlayer.Builder(context).build() }
```

第二次投屏仍播上一个视频。反向的 `LiveScreen` 用 `DisposableEffect(channel.url)` 里 `release()`，key 变化时会 release 已释放实例再 prepare → 崩溃。

**修复**：`remember(target.url)` / `remember(channel.url)`，让播放器与地址生命周期绑定。

### F4 返回键一次退两级（中危，已修）

`PlayerScreen` 在 `onPreviewKeyEvent` 里消费 `Key.Back` 的 KeyDown，但 KeyUp 分支直接 `return false` → Activity 的 `BackHandler` 再触发一次。`LiveScreen` 同样。

**修复**：删除预览处理器里的 Back 分支，统一交给 `BackHandler`。

### F5 播放错误面板与选集抽屉不可操作（中危，已修）

`PlayerScreen` 根 Box 的预览处理器无条件吞掉方向键与 OK，预览阶段先于子节点焦点处理 → 错误面板的「重试/下一集/返回」和 `EpisodeChip` 永远收不到按键。播放失败即死局。

**修复**：`drawerVisible || error != null` 时放行方向键与 OK。

### F6 看完一集后续播跳到片尾（中危，已修）

`STATE_ENDED` 时用 `exo.duration` 同时当 position 存盘 → 历史进度 100% → 下次「继续播放」跳到片尾立刻 ENDED。

**修复**：`saveProgress(..., finished = true)`，看完的一集记为 `positionMs = 0` 并把 `episodeIndex` 前移一集。

### F7 分类/直播加载无取消，旧结果覆盖新结果（中危，已修）

`loadCategory` 串行 `forEach`（8 个源 × 14s 超时 ≈ 112s），且协程不取消，快速切分类时旧协程回来会覆盖新分类。`loadLive` 同样。

**修复**：`categoryJob?.cancel()` 后再起新任务；改用 `async/awaitAll` 并行抓取；`Repository.categoryCache` 改 `ConcurrentHashMap`。

### F8 切集动画状态泄漏与 `isValidVodId` 边界（轻微，已修）

`detail.ts:39` 的 `let detailRoot = ''` 后面必被赋值，属于无效初始化（ESLint `no-useless-assignment`）。

**修复**：改为 `let detailRoot: string`。

### F9 `normalizeStreamUrl` 遇空格/中文 baseUrl 整源失败（中危，已修）

```kotlin
// 修复前：baseUrl 含空格 → URISyntaxException 被 runCatching 吞掉 → 返回 null
java.net.URI(baseUrl ?: "").resolve(trimmed).toURL()
```

一行都解析不出来时，整个直播源被判定为「未解析到可用频道」。

**修复**：先对 baseUrl 做最小转义（空格 → `%20`）再 resolve，失败才退化为「只认绝对地址」，并显式校验 http(s) 协议。

## 六、未修复 / 已知限制

1. **`fe80::/10` 只判字面前缀**：`feb0::1` 这类地址可绕过 IPv6 链路本地判断。价值低（需要攻击者控制上游解析），暂未处理。
2. **DNS rebinding**：`assertAllowedTarget` 解析一次、`fetch` 再解析一次，理论上有 TOCTOU 窗口。彻底解决需用自定义 `lookup` 固定 IP，改动面较大，暂记录在案。
3. **`http:fetch` 仍跟随重定向**：已加协议/内网/方法/大小约束，但重定向后的目标不再复核（媒体代理已修，这条因为要走真实元数据接口暂保留）。后续可复用 `fetchChecked`。
4. **TV 端 `usesCleartextTraffic=true`**：采集站绝大多数是 http，属功能性必需；已在设置页说明风险。
5. **`allowBackup=true`**：观看历史/收藏会进云备份，如需隐私可改 `false`。
