1. **电视端 DLNA 接收端存在必然失败的字节/字符混淆**，导致「中文片名的投屏」100% 失败（P1 `H1`，新发现）；

4. **桌面渲染层的失败转移有两条会留下不可恢复的界面状态**：全源失败后黑屏且无任何按钮（`RPL-01`）、换源成功后把用户刚切的集数改回旧值（`RPL-02`）；
5. **电视端焦点与遥控器处理是全域测试盲区**：首焦点丢失（`H3`）、错误面板消失后遥控器整体失灵（`T-1`）、直播错误面板按钮永远不可达（`T-2`）、详情页换源抢焦点（`M13`）、投屏页无可聚焦元素（`M14`）—— 其中前三条都能稳定复现，且没有任何 Compose UI 测试兜底；
6. **桌面端「导入配置」是唯一能一次点击丢失全部本地数据的路径**：`parseSnapshot` 把任意 JSON 都当合法快照，`replaceAll` 不做任何校验与确认，导错文件即清空全部源/历史/收藏且内置源不会自动恢复（`H4`，原 `M11` 升级）。

## 2. P1 高危

### H1. 电视端 DLNA 接收端把 `Content-Length`（字节）当字符数读，中文片名投屏必然失败

- **位置**：`apps/androidtv/app/src/main/java/org/libretv/tv/cast/DlnaServer.kt:144`、`:169-184`
- **证据**：

```kotlin
val reader = BufferedReader(InputStreamReader(socket.getInputStream(), Charsets.UTF_8))   // :144
...
val declared = headers["content-length"]?.toIntOrNull() ?: return ""                      // :170
val buffer = CharArray(declared)                                                          // :176
while (read < declared) {
    val r = reader.read(buffer, read, declared - read)                                    // :179
```

- **机理**：`Content-Length` 是**字节数**，而 `reader.read(char[], …)` 读的是**字符数**。SOAP 请求体里的 `<dc:title>` 带着中文片名（桌面端 `apps/desktop/src/main/dlna.ts:197-202 buildMetadata` 就是把标题塞进 `dc:title`），UTF-8 下一个汉字 3 字节，实际字符数远小于 `declared`。循环永远凑不满 `declared`，第二次 `read()` 阻塞在已无数据的 socket 上，直到 `DlnaServer.kt:55 CLIENT_TIMEOUT_MS = 5_000` 的 `soTimeout` 抛 `SocketTimeoutException`；`handleClient`（`:141-163`）没有外层兜底，异常被 `:134` 的 `runCatching` 吞掉，**一个字节的响应都不会写回**。
- **影响**：只要片名含中文（几乎全部内容），SetAVTransportURI 就超时失败，发送端（桌面 `dlna.ts` / 手机投屏 App）表现为"投屏无响应"。纯 ASCII 标题才成功——而 `tools/mock-dlna/test.mjs:28` 用的偏偏是中文标题，却因为 mock 服务端是 Node（按字节正确解析）而全绿，**测试从未覆盖电视端解析器**。
- **修法**：按字节读再解码。`val bytes = ByteArray(declared)` + 对 `InputStream` 循环 `read(bytes, read, declared - read)`（或用 `readNBytes`），最后 `String(bytes, 0, read, Charsets.UTF_8)`；顺带补一条 JVM 单测（把 SOAP 报文写成 `ByteArrayInputStream`，标题用中文，断言 `CurrentURI` 解析正确）。

### H2. 多码率点播源被判定为直播，分片缓存与预取整体失效

- **位置**：`apps/desktop/src/main/proxy.ts:650`
- **证据**：

```ts
// 没有 `#EXT-X-ENDLIST` 就是还在滚动的直播列表（master 列表同理）：
const liveMode = isLive || !text.includes('#EXT-X-ENDLIST');
```

- **机理**：按 HLS 规范（RFC 8216），**master playlist 本来就不含 `#EXT-X-ENDLIST`**，只有媒体列表（VOD 的最后一页）才有。于是任何"多码率"源（master → 多个 variant）第一次请求就被判成 `liveMode = true`，`rewritePlaylist`（`:230-261`）把 `&live=1` 写进所有子地址；下游每个 variant、每个分片都带着 `live=1`，而 `:567 const cacheEligible = route === '/p' && !rangeHeader && !isLive;` 因 `isLive` 为真永假、`:879` 的 `Cache-Control` 变成 `no-store`、`:673 if (upstream.ok && !liveMode)` 使预热被整体跳过。
- **影响**：对"master 形态"的源（代码注释 `:726` 自己承认是国内采集站主流形态），`SegmentCache`、`/prefetch`、浏览器 HTTP 缓存**三者全部空转**：每次起播/拖动都要整段回源，流量与首帧时间按倍增长；而 `Watch.tsx:214-216` 点播时仍会触发 `prefetchSegments`（`lib/bridge.ts:149-160`），预取钻进 variant 下载的分片**永远不会被命中**——纯烧带宽。
- **修法**：按 `#EXT-X-STREAM-INF` 判定 master（或 `contentType` 含 `mpegurl` 且存在 `#EXT-X-STREAM-INF`）时**不传播 `live`**，让 variant 自己按 `ENDLIST` 判定；判据改成"master → 子列表不确定 → 不带 live；媒体列表无 ENDLIST → 带 live"。

### H3. 电视端首焦点丢失：分类页与"从导航栏进入"两个入口都拿不到焦点

- **位置**：`apps/androidtv/app/src/main/java/org/libretv/tv/ui/CategoryScreen.kt:65-70`、`:121`；`ui/HomeScreen.kt:53-61`；`ui/SearchScreen.kt:56`；根因在 `AppViewModel.kt:485`
- **证据**：

```kotlin
// CategoryScreen.kt:65-70
LaunchedEffect(state.key) {
    if (!focusRestored) {
        runCatching { firstFocus.requestFocus() }
        focusRestored = true
    }
}
// :121  只有「当前分类」这一项拿到 requester，而它在 LazyRow 里可能未被组合
focusRequester = if (selected) firstFocus else null,
```

```kotlin
// AppViewModel.kt:485 —— 全仓零调用点
fun endNavFocusHold() { navFocusHold = false }
```

- **机理**：
  1. `firstFocus` 只挂在 LazyRow（`:108`）中被选中项上；8 个分类中文标签合计宽度超过可视宽度时，靠后的项（如「短剧」「体育」「纪录片」）**没有组合**，`requestFocus()` 抛 `FocusRequester is not initialized` 被 `runCatching` 吞掉；紧接着 `:68` 无条件把 `focusRestored` 置 true，`LaunchedEffect` 的 key 又只在分类变化时重跑，**整页生命周期内不会再试第二次**。从首页的分类胶囊直接进入靠后分类即命中。
  2. 首页/搜索页用 `LaunchedEffect(Unit)` + `if (vm.navFocusHold) return@LaunchedEffect` 早退。`navFocusHold` 由"焦点移进导航"置 true，设计上应由"用户在导航上按 OK 选页"收尾（`ui/App.kt:66-75` 的注释明确这么写），但 `endNavFocusHold()` **全仓没有任何调用点**，`releaseNavFocusHoldSoon()` 只是延时兜底。用遥控器在导航栏按 OK 进页时，新页的组合发生在 `navFocusHold == true` 期间，早退后再无重试。
- **影响**：进入页面后屏幕上没有焦点框，遥控器方向键的落点不可预期：在分类页按 ↓ 可能回到已被销毁的首页胶囊上，在搜索页按 ↓ 只在导航列里移动（等于连续切页）。电视端没有鼠标兜底，这是"看起来坏了"的典型表现。
- **修法**：分类页先 `scrollToItem(index)` 再 `requestFocus`，并把 `focusRestored` 换成"用户尚未自行移动焦点"的标记；`vm.go()` 里显式调用 `endNavFocusHold()`（让注释承诺的行为真正存在）；首焦点统一改成"`repeat(n) { delay(80); if (requestFocus().isSuccess) return }`"，不要单次 + 静默吞异常。

### H4. 配置导入可一键清空全部本地数据，且没有任何确认

- **位置**：`apps/desktop/src/renderer/src/pages/Settings.tsx:464-478`（`importAll`）、`packages/core/src/storage.ts:186-218`（`parseSnapshot`）、`apps/desktop/src/renderer/src/lib/store.ts:371-381`（`replaceAll`）
- **证据**：

```ts
const snapshot = parseSnapshot(file.content);
if (!snapshot) {
  toast.err('不是可识别的 LibreTV 配置');
  return;
}
replaceAll(snapshot);
toast.ok(`已导入 ${snapshot.sources.length} 个源、${snapshot.history.length} 条历史`);
```

- **机理**：`parseSnapshot` 只判断"能 `JSON.parse` 且是对象"，缺字段一律回落成空数组 + 默认 settings，所以 `{}`、`{"foo":1}`、被截断但仍能解析的备份都会返回一个"合法快照"。随后 `replaceAll` 逐字段 `?? 当前值` 覆盖，**没有确认框、没有版本校验、没有条目级校验**：不查 URL 协议、不去重、不套 `HISTORY_LIMIT(200)`/`FAVORITE_LIMIT(500)`，`history`/`favorites` 直接 `as HistoryEntry[]`。更糟的是导入不重置 `defaultsSeeded`，而 `seedDefaults` 只在 App 启动时跑一次 —— 导错文件后内置源**不会自动回来**，源列表永久为空，只能手输或重新导入一份正确备份。
- **影响**：用户在「导入配置」里选错一个 `.json`（或备份被截断、或被手改坏）→ 全部点播源、直播源、观看历史、收藏、设置瞬间清空，无撤销、无自动备份，界面还显示绿色「已导入 0 个源、0 条历史」。这是本仓库唯一能"一次点击丢失全部本地数据"的路径，因此按 P1 处理（原编号 `M11`）。
- **修法**：①`parseSnapshot` 做元素级校验（`history` 走 `normalizeHistoryEntry`、`favorites` 校验 `id/url`），非法条目计数 > 0 时返回告警而不是静默；②导入前要求 `version === 1` 且 `sources.length + liveSources.length + history.length > 0`；③弹 `confirm` 并列出「将覆盖 N 个源 / M 条历史」；④覆盖前把当前状态写进一个备份键，提供「撤销上次导入」；⑤`replaceAll` 内统一做源去重/URL 校验/历史上限裁剪。

## 3. P2 中危

### M1. `http:fetch` / `http:stream` 只校验入口地址、仍跟随跳转 —— SSRF 边界可被一次 302 绕过

- **位置**：`apps/desktop/src/main/index.ts:222`（入口校验）、`:239`（fetch）、`:289`、`:313`（stream）
- **证据**：`redirect: 'follow'`；对比 `apps/desktop/src/main/proxy.ts:200` 已改为 `redirect: 'manual'` + 逐跳 `assertAllowedTarget`。
- **机理/影响**：媒体代理已经把"逐跳校验"做对了，但同一份边界在 IPC 两条通道上没有落地：任何远程页面/源只要回一个 `302 Location: http://192.168.1.1/` 就能让主进程去访问内网。`docs/audit-2026-10.md` 把这条列为"已知未修"，但 `index.ts:219` 的注释写的是"与媒体代理同一套边界" —— 注释与实现相反，属于误导性文档，建议本轮一并修掉（直接复用 `fetchChecked`）。
- **修法**：两条通道都改为 `redirect: 'manual'` + 最多 5 跳，每跳 `assertAllowedTarget`，并删掉那句错误注释。

### M2. `http:fetch` 先 `arrayBuffer()` 全量入堆再判 16MB

- **位置**：`apps/desktop/src/main/index.ts:242-244`
- **证据**：`const buf = new Uint8Array(await res.arrayBuffer()); if (buf.byteLength > MAX_IPC_BODY_BYTES) return fail(413, '响应体过大');`
- **机理/影响**：M1 的流式限长只覆盖了 `proxy.readLimited`，这条 IPC 仍是"读完才发现超了"，且随后还要同时返回 `text` 与 `bytes` 两份。一个 2GB 的响应可以先把主进程打爆。同文件的 `http:stream`（`:336-339`）反而是流式限长，两条通道标准不一致。
- **修法**：复用 `proxy.readLimited(res, MAX_IPC_BODY_BYTES)`。

### M3. `dlna:stop` 不做同源/协议校验，只 `dlna:cast` 有

- **位置**：`apps/desktop/src/main/index.ts:417-424`（stop）对比 `:403-410`（cast，校验 `controlUrl` 协议与主机）
- **机理/影响**：渲染层（一旦被 XSS 或恶意源数据影响）可把任意 URL 当 `device.controlUrl` 传进 `dlna:stop`，让主进程向任意地址 POST 一段 SOAP。S3 只修了 cast 一侧。
- **修法**：抽 `assertLocalControlUrl(device)`，两个 handler 共用。

### M4. DLNA 响应体无字节上限（设备描述与 SOAP 响应）

- **位置**：`apps/desktop/src/main/dlna.ts:83`（`parseDeviceDescription(await res.text(), location)`）、`:228`（`soap` 里 `await res.text()`）
- **机理/影响**：只有 4s/6s 超时，没有长度上限。局域网内任意主机（SSDP 本来就只校验同网段，挡不住同网段恶意设备）可以在超时前推几百 MB 让主进程 OOM。
- **修法**：复用 `readLimited(res, 256 * 1024)`。

### M5. DNS rebinding TOCTOU：校验用缓存的解析结果，连接时重新解析

- **位置**：`apps/desktop/src/main/proxy.ts:167-170`（`lookupCached`）→ `:200`（把主机名交给 undici 重新解析）
- **机理/影响**：`docs/audit-2026-10.md` 已列为已知限制，但它是**唯一能击穿 S1 逐跳校验**的路径（校验时解析到公网、连接时解析到 127.0.0.1），实际风险高于"已知限制"这个措辞。60s 缓存把攻击窗口拉长到分钟级。
- **修法**：解析后把 IP 直接用于连接（`undici` 的 `connect`/自定义 `lookup` 返回已校验的 IP），或对私网判定失败的地址拒绝并**不缓存失败结果**。

### M6. IPv6 字面量与私网判定有缺口

- **位置**：`apps/desktop/src/main/proxy.ts:163`（`if (net.isIP(host))`）、`:112`（`startsWith('fe80')`/`fc`/`fd`）、`:114`（`::ffff:`）
- **机理**：WHATWG URL 的 `hostname` 对 IPv6 **保留方括号**（`new URL('http://[::1]/').hostname === '[::1]'`），`net.isIP('[::1]') === 0`，于是走到 `dns.lookup('[::1]')` 靠"解析失败"间接拦住，错误文案变成"域名解析失败"；`fe80::/10` 只判字面前缀，漏 `feb0::/10`（`feb0`–`febf`）；`::ffff:` 只认十进制点分写法，漏 `::ffff:7f00:1` 这种十六进制压缩形式。
- **影响**：目前没有造成实际绕过（都被别的失败路径挡住），但"防护靠巧合"——去掉 DNS 解析失败这一环就会漏。`proxy.test.ts:41-42` 的 `[::1]`/`[::ffff:127.0.0.1]` 用例正是靠解析失败通过，删掉私网判定也不会红。
- **修法**：先 `host.replace(/^\[|\]$/g, '')` 再 `net.isIP`；私网判定改用 `ipaddr` 式位运算（或至少展开 `::ffff:` 的十六进制形式）；测试改用"判定函数直测"而不是"端到端试探"。

### M7. URL 内嵌凭据的源 100% 不可播，且明文密码进日志/界面

- **位置**：`apps/desktop/src/main/proxy.ts:200`（`new Request(...)`）、`:480`（`sendText(502, \`代理失败：${err.message}\`)`）
- **机理**：undici 对含凭据的 URL 直接抛 `TypeError: Request cannot be constructed from a URL that includes credentials`；`assertAllowedTarget` 不剥 userinfo。
- **影响**：`http://user:pass@host/...` 这类源（部分采集站给的接口地址就是这种）在桌面端完全不可播；错误信息里还带着含明文密码的 URL，被打到界面和日志。
- **修法**：解析时把 userinfo 转成 `Authorization: Basic ...` 头，或在 `assertAllowedTarget` 里剥掉；所有错误文案统一过一遍 `redactUrl()`。

### M8. `/p` 原样透传上游 `Content-Type`，且错误响应也给 `immutable` 缓存

- **位置**：`apps/desktop/src/main/proxy.ts:874`（透传）、`:879`（`Cache-Control`）
- **证据**：`/i` 路由已用 `SAFE_IMAGE_TYPES` 收敛（`:606`、`:613` 的 `upstream.ok ? CACHE_SEGMENT : 'no-store'`），`/p` 两处都没跟上。
- **影响**：①远端可以把 `text/html` 当"媒体"回给渲染层（虽然 `<video>`/hls.js 不会执行它，但同域 `127.0.0.1` 的资源被当 HTML 提供是多余的攻击面）；②上游瞬时 403/404/500 会被浏览器按 `max-age=3600, immutable` 缓存一小时，用户"重试"也拿不到正确结果。
- **修法**：`/p` 只放行 `video/*`、`audio/*`、`application/vnd.apple.mpegurl`、`application/octet-stream`，其余降级为 `application/octet-stream` + `X-Content-Type-Options: nosniff`；`Cache-Control` 与 `/i` 对齐。

### M9. 跨源候选发现（按片名补源）对带标点/空格的片名失效

- **位置**：`packages/core/src/failover.ts:248`、`:254`、`:256`；归一化在 `packages/core/src/cms.ts:249-251`；**电视端同源缺陷** `apps/androidtv/app/src/main/java/org/libretv/tv/data/Repository.kt:191`、`:197`（`val wanted = keyword.lowercase()` 对 `Parsers.normalizeTitle(item.name).lowercase()`）
- **证据**：

```ts
const wanted = keyword.toLowerCase();                          // :248 未归一化
const name = normalizeTitle(item.name).toLowerCase();          // :254 去了空格/标点/符号
return name === wanted || name.includes(wanted) || wanted.includes(name);  // :256
```

- **机理**：`normalizeTitle` 会 `replace(/[\s\p{P}\p{S}]+/gu, '')`，而 `wanted` 保留了空格与标点，三条比较对 `名侦探柯南：黑铁的鱼影`、`The Matrix`、`三体（2023）` 全部为 `false`。
- **影响**：失败转移走到"候选链空了，按片名再补一轮"时直接补不到（`Watch.tsx:152`、`AppViewModel.kt:1072` 两条链路都受影响），用户看到的是"所有源都播不了"而不是自动切到别的源。单测 `failover.test.ts:296-305` 用的片名是 `流浪地球`（无标点无空格），所以一直绿。
- **修法**：`const wanted = normalizeTitle(keyword);`（Kotlin 侧 `val wanted = Parsers.normalizeTitle(keyword).lowercase()`），并补一条带标点的用例。

### M10. 分类页"全部源失败"的空结果仍会写 5 分钟缓存

- **位置**：`packages/core/src/categories.ts:412-421`（重复源记 `ok: true`）、`:551`（`const answered = outcomes.some((o) => o.ok)`）
- **机理**：重复 URL 的源被折叠成 `duplicated` 条目却把 `ok` 置真，于是"全源超时"时 `answered` 依然为真，空结果进 `browseCache`（`:548-550` 的注释本意是"全失败不缓存，让用户重进能重试"）。
- **影响**：一次网络抖动会让该分类在 5 分钟内稳定显示"没有内容"，且用户重进页面也刷不出来。
- **修法**：`duplicated` 条目用单独的 `folded` 标记（不参与 `answered`），或者 `answered` 只看 `outcome.supported && outcome.ok`。

### M11. 快照导入不校验结构：任意 JSON 都会清空数据（**已升级为 P1，见 §2 H4**）

### M12. `MAX_STREAM_BYTES` 超限后静默截断，但仍回 200 + 上游 `Content-Length`

- **位置**：`apps/desktop/src/main/proxy.ts:923`
- **证据**：`if (total > MAX_STREAM_BYTES) return false;`
- **影响**：超过 1GB 的媒体流，前面已经按上游 `Content-Length` 写好响应头，到这里只停止搬运：客户端拿到半截文件、等到超时，且没有任何错误线索。
- **修法**：超限时 `res.destroy()`（并记一条 warn），或干脆在写头之前用上游 `Content-Length` 预判并回 413。

### M13. 详情页切换片源会把焦点从选集拽回"播放"按钮

- **位置**：`apps/androidtv/app/src/main/java/org/libretv/tv/ui/DetailScreen.kt:58`
- **证据**：`LaunchedEffect(target.item.vodId) { runCatching { playFocus.requestFocus() } }`
- **机理**：key 用了 `vodId`——用户在同片源 chips 里换源时 `vodId` 变化，effect 重跑，焦点被强制拉回顶部；且单次 `requestFocus` 失败即静默放弃（首帧节点可能尚未放置）。
- **影响**：长剧集里挑到第 20 集后换个源，焦点被抢回顶部，要重新按一路 ↓ 走回去。
- **修法**：只在"首次进入本影片"抢焦点（`remember` 已初始化过的 vodId 集合），并加重试。

### M14. 投屏页整页没有可聚焦元素

- **位置**：`apps/androidtv/app/src/main/java/org/libretv/tv/ui/CastScreen.kt:146`
- **机理**：整页只有 `Text`/`Panel`，无 `focusable`/`clickable`，也没有初始 `FocusRequester`。
- **影响**：从导航进入后焦点仍留在导航项上，按 ↓ 直接切到下一个页面——用户无法"停在"投屏页看地址。
- **修法**：给状态面板或一个"刷新/复制地址"按钮挂焦点并请求。

### M15. 导入订阅无重入保护，按钮也不置灰

- **位置**：`apps/androidtv/.../ui/SettingsScreen.kt:174`、`AppViewModel.kt:1439-1464`
- **机理**：`importing` 只用于改文案，没有 `if (importing) return` 守卫，`TvButton` 也没有 `enabled` 参数。
- **影响**：遥控器重复按 OK 会并发跑两次导入，`store.update` 的 read-modify-write 可能把同一批源重复追加、勾选集合互相覆盖。
- **修法**：入口加守卫；`TvButton` 增加 `enabled`。

### M16. 添加源校验失败时仍清空输入框

- **位置**：`apps/androidtv/.../ui/SettingsScreen.kt:91-94`
- **机理**：`vm.addSource(...)` 是异步且带校验的（非 `http` 开头会 toast 后 return），UI 侧无条件把三个输入框清空。
- **影响**：输错一个字符，名称/地址/详情全部丢失，只能重打。
- **修法**：`addSource` 返回布尔，成功才清空。

### M17. 错误提示因运算符优先级被吞掉一半

- **位置**：`apps/androidtv/.../ui/CategoryScreen.kt:170-172`
- **证据**：

```kotlin
"请求全部失败" +
    if (state.failureReason.isNotBlank()) "（${state.failureReason}）" else "" +
        "，通常是网络不通或采集站限流。稍后可重新进入本页重试。"
```

- **机理**：`else` 分支实际是 `"" + "，通常是…"`，于是 **`failureReason` 非空时**（也就是最需要引导的时候）整句后半段消失，只剩"请求全部失败（xxx）"。
- **影响**：全源失败时用户看不到"稍后重试"的引导。
- **修法**：括号部分提取成 `val reason = if (...) "（…）" else ""` 再拼接。

## 6. 电视端（Android TV）复核

> 范围：`apps/androidtv/app/src/main/java/org/libretv/tv/` 全部 Kotlin 源码（7859 行）与 13 个测试文件（1241 行、123 个 `@Test`）。
> 本节只记电视端独有结论；跨端问题（M9 补源归一化、M13 详情页焦点、M14 投屏页焦点、M15/M16/M17）已在前面的清单里。

### 6.1 电视端高危

#### T-1. 错误面板消失后无人接管焦点，遥控器除返回键外全部失效

- **位置**：`apps/androidtv/app/src/main/java/org/libretv/tv/ui/PlayerScreen.kt:290-295`、`:306`
- **证据**：

```kotlin
LaunchedEffect(error) {
    if (error != null) {
        delay(60)
        runCatching { errorFocus.requestFocus() }
    }
}
```

- **机理**：面板出现时把焦点送到 `errorFocus`（错误面板里的「重试」按钮），但 `error` 变回 `null` 的四条路径（`:177` 自动换源成功、`:191` 切集、`:419` 换源重试、`:424` 重试）都没有把焦点还回去。持有焦点的那个 `TvCard` 随面板一起被移除，Compose 会 clearFocus，此后根 `Box`（`:297-303`）不再持有焦点，`onPreviewKeyEvent` 收不到任何键；返回键仍然有效是因为它走的是 `MainActivity` 的 `BackHandler`。
- **影响**：播放失败后只要按过「重试 / 下一集 / 换源重试」，或者自动换源成功过一次，暂停、快进、选集、换源、菜单全部按不动，只能退出重进（并丢掉当前进度）。电视端没有鼠标兜底。
- **修法**：把恢复改成双向 —— `LaunchedEffect(error) { delay(60); runCatching { (if (error != null) errorFocus else focusRequester).requestFocus() } }`；或在四个 `error = null` 分支后统一请求根 `focusRequester`。

#### T-2. 直播错误面板的「重试 / 下一个频道 / 返回」永远拿不到焦点

- **位置**：`apps/androidtv/app/src/main/java/org/libretv/tv/ui/LiveScreen.kt:385-413`（按键拦截）、`:430-443`（面板）
- **证据**：

```kotlin
Key.DirectionCenter, Key.Enter -> {
    if (exo.isPlaying) exo.pause() else exo.play()
    overlay = true
    true
}
```

- **机理**：`LivePlayerScreen` 的根 `Box` 在 `:349` 只请求一次焦点，而 `:385-413` 的 `onPreviewKeyEvent` 对所有方向键与 Enter **无条件返回 `true`**，没有点播页那种 `error != null` 的放行分支。于是焦点永远停在根 `Box`，`:430-443` 的三个按钮既不会被焦点遍历到（连 Down 也被换台吃掉），也收不到 Enter。
- **影响**：直播源加载失败（`:340-347` 的 8 秒无画面判定）后，三个按钮全部按不动 —— 与已修复的 F5 属同一类问题，只是当年只覆盖了点播页。用户只能盲按返回键退回列表。
- **修法**：拦截开头加 `if (error != null) return@onPreviewKeyEvent false`，并用 `LaunchedEffect(error) { if (error != null) { delay(60); runCatching { errorFocus.requestFocus() } } }` 把焦点交给「重试」；`error` 归 null 时再把焦点交还根 `Box`。面板三个按钮需要各持一个 `FocusRequester`。

### 6.2 电视端中危

#### T-3. F6「看完一集」记录被进度监测与销毁保存覆盖（部分回归）

- **位置**：`ui/PlayerScreen.kt:219-229`（ENDED 写入）、`:246-265`（每 4 秒监测）、`:151-153`（onDispose）；`AppViewModel.kt:1006-1040 saveProgress`
- **证据**：

```kotlin
// PlayerScreen.kt:260-262
if (tick % 4 == 0 && position > 0) {
    vm.saveProgress(current, currentIndex, position, duration)
}
```

- **机理**：`STATE_ENDED` 时 `:223` 已写入 `finished = true`（位置 0、集数 +1）；但 `while (true)` 的监测循环不会停，ENDED 之后 `position == duration > 0`，于是每 4 秒再写一条 `finished = false`、`positionMs = duration`、`episodeIndex = index` 的记录。`saveProgress` 按 `id = "${sourceKey}:${vodId}"` upsert，后写覆盖先写；`:151-153` 的 `onDispose` 又用 `exo.currentPosition`（= duration）覆盖第三次。
- **触发条件**：`autoplayNext` 关闭（`Models.kt:177`，用户可改）或播到最后一集（`next` 越界不换集）。
- **影响**：历史被记成「本集看到片尾」，下次进入 `PlayerScreen.kt:204-207` 命中 `hist.episodeIndex == index && hist.positionMs > 15_000` 直接 `seekTo(duration)` → 秒进 ENDED，表现为「刚打开就播完」。这正是 F6 修好之前的老症状。
- **修法**：监测与销毁保存都排除完成态（`if (exo.playbackState != Player.STATE_ENDED && position < duration - 1_000)`）；`onDispose` 时若已 ENDED 则改传 `finished = true`。

#### T-4. 换源成功后 `play()` 被执行两次

- **位置**：`ui/PlayerScreen.kt:175-179`（`tryFailover` 内显式 `play()`）与 `:190-199`（`LaunchedEffect(current.source.key, current.vodId, index)`）
- **机理**：`tryFailover` 先改 `current`/`index` 再立刻 `play()`；同一次状态写入让 `LaunchedEffect` 的键变化，下一帧又执行一次 `SegmentPrefetch.start` 与 `play()`，等于连续两次 `setMediaSource + prepare`。
- **影响**：恰在最需要快速起播的失败转移时刻多一次清单拉取与一次 prepare；弱网盒子更容易二次超时，把用户推进下一轮换源。
- **修法**：`tryFailover` 只更新 `current`/`index`，起播统一由 `LaunchedEffect` 负责。

#### T-5. 换源提示存在期间（最长十几秒 + 成功后再 2.4s）遥控器除 Down 外全被吞

- **位置**：`ui/PlayerScreen.kt:306`（条件 `drawerVisible || error != null || note != null`）、`:165`、`:181-182`
- **机理**：`tryFailover` 一进来就设 `note = "…正在切换片源…"`，每个候选解析成功后还要 `delay(2_400)` 才清空。窗口内 OK/左右/上/菜单一律 `return false`。
- **影响**：换源过程中按 OK 想暂停、按左右想快进都没反应；成功换源后的前 2.4 秒操作也会丢失，用户会认为遥控器失灵。
- **修法**：`note` 只做展示，不参与拦截（条件改成 `drawerVisible || error != null`）。

#### T-6. 按 Home 回桌面后仍继续解码出声

- **位置**：`ui/PlayerScreen.kt:122`、`ui/LiveScreen.kt:305`；`MainActivity.kt` 无 `onStop`
- **机理**：播放器只在 `DisposableEffect(Unit).onDispose` 里 release；Activity 进 `onStop` 时组合不销毁。全仓 `grep` 无 `LifecycleEventEffect`/`ON_STOP`，`Playback.build` 默认 `playWhenReady = true`，按 Home 也不会触发音频焦点变化。
- **影响**：回桌面或切到别的应用后电视仍在解码并出声，持续占用硬件解码器与带宽，用户以为应用关不掉。
- **修法**：`LifecycleEventEffect(Lifecycle.Event.ON_STOP) { exo.pause() }`（`lifecycle-runtime-compose:2.8.7` 已在依赖里），`ON_START` 再恢复。

#### T-7. 长按方向键换台无节流，每换一台就重建一个 ExoPlayer

- **位置**：`ui/LiveScreen.kt:305`（`remember(current.url) { Playback.build(context)… }`）、`:368-377`（`switchTo`）、`:317-319`（READY 即放开闸门）
- **机理**：`switching` 闸门在到达 `STATE_READY` 就复位，而遥控器长按方向键每秒约 10 个 KeyDown，于是每个台刚起播就接受下一次切换，每次新建并 release 一个 ExoPlayer（含 `DefaultLoadControl` 与音视频 renderer）。
- **影响**：按住方向键时以每秒 1-2 次的节奏反复创建/释放播放器与 MediaCodec，Amlogic 等低端盒子常见 codec 申请失败、黑屏数秒甚至 `PlaybackException`，同时不断重打直播流请求。
- **修法**：`switchTo` 加时间节流（`lastSwitchAt`，<400ms 直接返回）；更彻底是常驻一个 ExoPlayer（`remember` 不绑 url），换台走 `setMediaItem`。

## 7. 桌面渲染层（React）复核

> 范围：`apps/desktop/src/renderer/src/` 全部 4633 行（Watch 833 行 / Live 775 行 / Settings 547 行 / Category 约 480 行 / store 约 520 行 + 组件与 lib）。

### 7.1 渲染层高危

#### RPL-01. 候选源全部失败时进入"无面板"死态：黑屏 + 换源提示永不消失

- **位置**：`apps/desktop/src/renderer/src/pages/Watch.tsx:140-191`（failover）、`:148-149`、`:168`、`:177`、`:227-239`（handleFatal）、`:620-664`（面板条件）
- **证据**：

```ts
if (untried.length === 0) {
  if (discoveredRef.current) return false;
}
```

- **机理**：`failover` 每轮开头 `setError(null)`，只有在"确实还有候选"时才继续；`untried` 为空且已做过一次 `discoverCandidates` 时直接 `return false` —— **既不 `setError(lastError)`，也不清 `failoverNote`**（清 note 的 `setTimeout(…, 2600)` 只挂在成功分支）。`handleFatal` 调用处写的是 `void failover(message)`，返回值被丢弃，所以上层也不知道失败了。渲染侧两个面板的条件分别是 `loading && !error` 与 `error &&`，此时 loading=false、error=null → 两个都不渲染。
- **影响**：所有源都播不了时（采集站限流、片源全挂），用户看到的是纯黑播放区 + 顶部永久残留「正在切换到「某某源」…」的提示，没有任何换源/重试按钮，只能按 Esc 退出。这是最常见的"看不了一部剧"路径，属于必修的用户可见死态。
- **修法**：`failover` 三条失败出口统一 `setError(lastError); setFailoverNote(null);`；`handleFatal` 用 `const ok = await failover(message); if (!ok) setError(message)` 兜底；面板条件改成 `loading || error || exhausted` 三态。

#### RPL-02. 换源成功后把用户刚切的集数静默改回旧值

- **位置**：`apps/desktop/src/renderer/src/pages/Watch.tsx:168-179`（`setIndex`）、`:140-161`（等待窗口）
- **证据**：

```ts
setIndex(pickEpisodeIndex(index, parsed.episodes.length))
```

- **机理**：`index` 是 `failover` 建立时闭包捕获的值；`failover` 在改 `index` 之前先 `await discoverCandidates`（最多 8s）再 `await fetchDetail`（最多 8s）。这段窗口里用户按「下一集」或点选集，`setIndex` 生效；等 failover 回来，它用旧 `index` 覆盖，把集数改回去。
- **影响**：弱网换源时"切集无效"的玄学现象，且播放位置与集数错位（视频已经换了集，进度条按旧集算），用户很容易判定为"播放器坏了"。
- **修法**：`setIndex((cur) => pickEpisodeIndex(cur, parsed.episodes.length))`；并引入 `episodeTokenRef`，failover 前后比对 token，不一致就放弃这次写入。

### 7.2 渲染层中危

#### RPL-03. 直播刷新没有取消能力：反复点「重新加载」会叠加多份全量下载

- **位置**：`apps/desktop/src/renderer/src/pages/Live.tsx:86`（runId）、`:159-181`（加载）
- **证据**：

```ts
await Promise.allSettled(
  liveSources.map((source) => fetchLivePlaylist(source.url, http, { onChannels, timeoutMs: 90_000, idleTimeoutMs: 20_000 })),
)
```

- **机理**：既没有 `AbortController`，Options 里也没有 `signal`；`runId` 只用来丢弃过期的 `setState`，网络与 IPC 流照旧跑完。`/stream` 请求最长 90s，单份直播源 2.5MB+（默认 Collect-IPTV）。
- **影响**：连点 3 次「重新加载」= 3 份最长 90s 的并行下载，渲染层每秒被 `onChannels` 回调灌入三倍批次（配合 RPL-09 的全量重建），弱网下界面冻结；离开页面后这些请求仍在继续。安卓端 F7 已修同类问题，桌面端漏了。
- **修法**：`useRef<AbortController>`，每次加载先 `abort()` 再新建，把 `signal` 透传给 `fetchLivePlaylist`（core 的 `http.stream` 已支持 `signal`）；`onChannels` 里先比对 `runId`。

#### RPL-04. 退出播放页的进度保存是死代码

- **位置**：`apps/desktop/src/renderer/src/pages/Watch.tsx:309-318`（cleanup 顺序）、`:344`（onPause）
- **机理**：播放 effect 的 cleanup 先执行 `video.pause(); video.removeAttribute('src'); video.load()`，currentTime 被归 0；退出保存的 cleanup 注册得更晚、执行也更晚，读 `video.currentTime > 0` 恒 false。`onPause` 监听在同一个 cleanup 里已被移除。
- **影响**：退出时最后 ≤5 秒（timeupdate 节流窗口）进度丢失；观感上是"暂停后直接退出会回退几秒"。
- **修法**：cleanup 里先读 `const at = video.currentTime` 再拆 src；或把 `persistProgress` 提到 cleanup 的第一句。

#### RPL-05. 每 5 秒一次全量状态序列化写 localStorage

- **位置**：`apps/desktop/src/renderer/src/lib/store.ts:383-403`（persist 配置）、`pages/Watch.tsx:329`（`persistProgress` 节流 5s）
- **机理**：persist 的 `partialize` 包含 `sources`/`history`/`favorites`，`createJSONStorage(() => quotaSafeStorage)` 每次 `set` 都会 `JSON.stringify` 整个 slice 再同步写 localStorage（主线程）。
- **影响**：一集 45 分钟 ≈ 540 次全量序列化；history 满 200 条且每条带封面 URL 时，单次序列化十万字节量级，表现为每隔 5 秒一次可感知的掉帧；与 RPL-14/15 叠加时更容易触发配额异常。
- **修法**：进度写入单独走一个轻量 key（或 `sessionStorage`），history 只在"切集/退出/收藏"时落盘；persist 加 `migrate` 并显式声明 `version`。

#### RPL-06. hls.js 解码错误时"就地恢复"与"重建实例"互相抵消

- **位置**：`apps/desktop/src/renderer/src/pages/Watch.tsx:262-265`
- **证据**：

```ts
if (data.type === Hls.ErrorTypes.MEDIA_ERROR) {
  hls?.recoverMediaError()
  handleFatal('解码错误')
}
```

- **机理**：`recoverMediaError()` 是就地恢复，紧接着 `handleFatal` 走 `setReloadToken` 重建 hls 实例，恢复动作白做，同时 `recoverRef` 配额被消耗。
- **影响**：可自愈的解码抖动被升级成"换源"，用户在还能救的情况下被切到别的源。
- **修法**：`if (recoverCount < 2) { recoverCount++; hls.recoverMediaError() } else handleFatal(…)`。

#### RPL-07. failover 内部两个网络调用不响应卸载

- **位置**：`apps/desktop/src/renderer/src/pages/Watch.tsx:140-161`（`discoverCandidates` / `fetchDetail` 均未传 `signal`）
- **影响**：退出详情/播放页后最长 16s 仍在跑，回来时 `setState` 到已卸载或新挂载的组件上（React 18 不再报 warning，但会写入错误的 `error`/`failoverNote`）。
- **修法**：组件级 `AbortController` 透传 `signal`，cleanup 里 abort。

#### RPL-08. 直播刷新失败会先清空已有频道

- **位置**：`apps/desktop/src/renderer/src/pages/Live.tsx:109`
- **机理**：没有缓存命中时先 `setChannels([])` 再请求；请求失败后列表为空。
- **影响**：断网重进直播页看到"暂无频道"，而不是上次的列表（有缓存时反而正常，行为不一致）。
- **修法**：失败时恢复上一份 `channels`，只在成功或首次加载时替换。

#### RPL-09. 流式加载回调每 120ms 全量重建频道数组

- **位置**：`apps/desktop/src/renderer/src/pages/Live.tsx:147-157`
- **机理**：`onChannels` 里 `merged.push(...list)` 后整体 `setChannels(merged)`；`groups`/`counts`/`visible` 都是基于 `channels` 的派生值，每次都全量重算并让所有已挂载卡片重渲。
- **影响**：2000+ 频道时肉眼可见的输入延迟与滚动卡顿，且与 RPL-03 叠加会成倍放大。
- **修法**：`useDeferredValue` + 分批合并（每 500ms 一次），或改用 `useSyncExternalStore` 做订阅式增量。

#### RPL-10. 长时间挂同一频道时 EPG「正在播出」永远停在首次结果

- **位置**：`apps/desktop/src/renderer/src/pages/Live.tsx:500-520`
- **机理**：effect 键是 `[channel.epg, channel.tvgId]`，只在换台时跑一次，没有定时刷新；节目播完后文案仍显示上一档。
- **修法**：加 60s 定时器重算（`currentAndNext` 是纯函数，无需重新拉 XMLTV），或在节目 `stop` 时刻用一个 `setTimeout` 精确刷新。

#### RPL-11. XMLTV 解析在主线程同步跑全局正则

- **位置**：`apps/desktop/src/renderer/src/lib/live-epg.ts:37`
- **机理**：`parseXmltv(text)` 对整份 XMLTV（常见 5–20MB）连跑多轮全局正则，完全在主线程；`http.request` 也未传 `signal`。
- **影响**：换台瞬间整页卡住数百毫秒到数秒，播放器画面跟着停顿。
- **修法**：解析挪到 `Worker`（或主进程），并给请求加 `signal`。

### 8.1 数据层中危

#### D-1. 元数据与分片请求没有响应体大小上限（桌面侧 M1 的同类问题，电视端未修）

- **位置**：`apps/androidtv/app/src/main/java/org/libretv/tv/data/Net.kt:58-66`（`getText`）、`:94-107`（`getBytes`）
- **证据**：

```kotlin
client.newCall(builder.build()).execute().use { response ->
    if (!response.isSuccessful) throw IOException("HTTP ${response.code}")
    response.body?.string() ?: ""
}
```

- **机理**：`ResponseBody.string()` 与 `bytes()` 都是"整个读完再交给你"，没有任何字节上限；只有 `forEachLine`（`:131`）是真正流式的。`getText` 被用于播放列表、EPG、详情 JSON、订阅源，`getBytes` 被用于预取分片。预取的 `SegmentLru.maxSegment = 4MB` 是**收下之后**才判的，来不及阻止一次性 `bytes()` 的分配。
- **影响**：采集站返回畸形大响应（常见于把整个片库 XML 当 JSON 返回）或恶意源时，电视盒子 192MB 堆直接 OOM 被系统杀掉，表现为"打开某个分类闪退"。桌面端同类问题在上一轮已按 M1 改成流式限长，电视端没跟上。
- **修法**：`getText` 用 `response.body!!.source()` + 读上限（如 4MB 文本 / 8MB 字节，超限抛 `IOException("响应过大")`）；`getBytes` 先看 `contentLength()`，再按 `maxSegment` 流式读满即止。

#### D-2. 目录缓存是"读-改-写"且无锁，并发预热会丢分类条目

- **位置**：`apps/androidtv/app/src/main/java/org/libretv/tv/data/Repository.kt:53-60`；并发来源 `AppViewModel.kt:295-324`（8 个分类各起协程并发写）、`:712`（前台 `loadCategory` 同时写）
- **证据**：

```kotlin

    val signature = current?.signature ?: return

    if (next === current) return
    catalog = next
    onCatalogChanged?.invoke(next)
}
```

- **机理**：`catalog` 虽是 `@Volatile`，但这里是典型的读-改-写：A 与 B 同时读到快照 S，各自产出 `S+分类A` 与 `S+分类B`，最后赋值的一方胜出，另一条分类的条目静默消失。`refreshCatalog` 明确用 `coroutineScope { CategoryKey.home.map { async { … repo.cacheCatalogItems(key, merged) } } }` 并发写 8 条。
- **影响**：冷启动预热后，`store.saveCatalog(repo.catalogSnapshot())` 落盘的快照可能少 1–7 个分类；用户点进这些分类时又得打一轮网络，离线时直接空白 —— 与"目录缓存保证弱网可用"的设计目标相悖。同一分类被前台与预热同时写时还会出现条目被旧数据覆盖。
- **修法**：`@Synchronized`（或 `synchronized(catalogLock)`）包住读-改-写与回调；更稳的做法是让 `catalog` 只在单一 `Mutex` 下更新，`saveCatalog` 也走同一把锁之后取快照。

### 8.4 请求生命周期补充复核（Net 与预取的取数路径）

#### D-6. 超时与取消都不中断在途请求：`execute()` 阻塞且没有 `call.cancel()`

- **位置**：`apps/androidtv/app/src/main/java/org/libretv/tv/data/Net.kt:58-66`（`getText`）、`:94-107`（`getBytes`）；等待方 `Repository.kt:96`、`:310`（`withTimeoutOrNull`）
- **证据**：

```kotlin

    withContext(Dispatchers.IO) {
        ...
        client.newCall(builder.build()).execute().use { response ->
```

- **机理**：`withTimeoutOrNull` 只能取消**协程**，而协程此刻阻塞在 `execute()` 这个同步调用里，没有任何一方调用 `Call.cancel()`。到点后 `withTimeoutOrNull` 返回 `null`、调用方以为已经放弃，但底层 OkHttp 调用仍在 IO 线程上继续读到 `readTimeout = 20s` 才结束。
- **影响**：切分类、切页、搜索新关键词时，旧请求全部继续占用 IO 线程与连接。`Dispatchers.IO` 默认 64 线程，而 `searchAll` 一次就能起 `源数 × 页数` 个请求，再叠加直播流的 2.5MB 下载，反复操作后请求排队、新请求迟迟拿不到线程，表现为"越用越卡、要杀进程才恢复"。桌面端 `proxy.ts` 是显式 `controller.abort()` + 上游 `destroy()`，电视端没有对应机制。
- **修法**：把 `execute()` 改成 `withContext(Dispatchers.IO) { call.execute() }` 并把 `call` 暴露出来，在 `invokeOnCancellation { call.cancel() }` 里取消；或直接用 `okhttp` 的 `Call.await()` 扩展（挂起式，取消即断）。

#### D-7. 搜索 / 详情 / 拼音 / 直播全部绕过并发闸门

- **位置**：`apps/androidtv/app/src/main/java/org/libretv/tv/data/Repository.kt:98`、`:105`、`:153`、`:160`、`:217`、`:397`；闸门只在 `Repository.kt:275`（`categoriesOf`）与 `:326`（`browseCategory`）使用
- **证据**：

#### D-8. `runCatching` 吞掉 `CancellationException`，取消被当成"源失败"

- **证据**：
